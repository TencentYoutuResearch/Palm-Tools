# External resources: Host owner-read facade

The dsh Host explicitly mounts `/api/kode/external-resources` within its existing `webServer` + `connection` lifecycle. The default connection registry is empty. There is no connection discovery, credential import, extra plugin installation, task authority, model call, polling loop or webhook receiver.

## Current integration state

The released dsh plugin APIs available in this checkout do not supply an approved, versioned TAPD/Gongfeng read-connection registry. Production therefore returns `state: disabled`, `reason: authorized_connection_registry_unavailable`. It neither creates a cache nor contacts a provider. A synthetic registry is passed directly to `mountExternalResources` only in isolated tests.

A future existing-plugin adapter must supply a trusted `Map(connectionId, ReadonlyProvider)` to `mountExternalResources`. Each provider requires an exact HTTPS origin/resource, explicit read capabilities, an opaque `authorizationRevision`, and a bounded `readJson` transport. The plugin authority must replace the provider and change this revision whenever account, grants, destination or approved display origins change. `readonlyTransport` accepts the existing credential system's header callback. No credential is accepted from the UI, stored in this module or sent to a model. There is intentionally no JSON/settings route to configure or enable connections here.

`instanceValidated` is false unless the trusted authority explicitly certifies an actual installation. `ready` means an approved read transport is present, never successful connectivity; `provider_health` remains `not_checked`. TAPD and Gongfeng have been exercised only with synthetic response fixtures.

## Owner UI contract

All requests use the existing dsh `connection.admit` owner admission. Sessions get 403; unauthenticated clients get the admission rejection. Responses use `Cache-Control: no-store`. No browser request can choose a provider URL, credential or transport.

- `GET ?op=status`: `{state, reason, authorized_connections, provider_health: "not_checked", dispatch: "disabled"}`. An initialized cache also returns `cache_capacity: {usage, limits, at_limit}` with aggregate counts and logical snapshot bytes only, no source text or identifiers. Missing registry and empty approved registry have distinct reasons. Cache initialization failure returns disabled / `cache_unavailable`, without paths or provider errors.
- `GET ?op=bindings&home_hub=...&host_id=...&workspace_id=...&root_ref=...`: `{items}`. All four scope fields are mandatory. Only bindings still authorized by the real Hub channel/audience are returned.
- `GET ?op=project&home_hub=...&host_id=...&workspace_id=...&root_ref=...&surface_id=...`: owner-only channel context. Returns `{scope, surface_id, audience_revision, bindings, connections}`. An enabled Hub channel must match the exact project scope. Same-project channels see the same existing bindings; each binding keeps its original source-channel and audience checks. Available connections must be explicitly scoped to this project by the provider authority. This operation neither binds nor reads the provider.
- `GET ?op=cards&binding=...&after=0&limit=30`: `{items, source, binding_revision, connection_revision, compatibility, last_sync, dispatch: "disabled"}`. Limit is 1–100. Continue with the last returned card's `cursor` until empty. Cursors are local snapshot observations, not provider revision order or a complete provider event feed. `last_sync` is the latest committed single-page source observation, or `null` when unavailable.
- `POST` JSON `{op: "bind", id, scope, surface_id, audience_revision, connection_id, source, enabled, expected_revision}`: compare-and-swap binding. `source` is `{provider, instance, resource}` and must exactly match an approved connection. New bindings use expected revision 0. The Host stamps `connection_revision`; the UI must not provide it. The channel, scope, connection ID and source are immutable. A revision update clears old cards, event observations, leases and receipts before the next snapshot.
- `POST` JSON `{op: "sync", binding_id, expected_revision, request_id, kind, page?, parent?}`: explicit single-page read. `page` defaults to 1 (maximum 100). Comments require `{kind, id}` parent. A completed exact request replays its receipt without refetch; changed arguments with the same request ID are rejected. Receipt: `{request_id, command_hash, updated, observed, origin: "external", dispatch: "disabled", binding_revision, last_sync}`. Legacy receipts may omit `last_sync`; replay never fabricates missing evidence or updates the binding's latest observation.

When disabled, resource operations return 503. Invalid request structure returns 400/413/415; unsupported methods return 405. Authorization/version/sync failures return a sanitized 409. A capacity rejection returns 409 with `code: "external_cache_capacity"`, the bounded `resource` name and a message confirming preservation of existing snapshots and receipts. There are no automatic retries. Duplicate query parameters and unsupported properties/operations are rejected.

Cards preserve source and parent identity and are always `origin: external`, `trusted_instruction: false`, `dispatch: disabled`. UI must render all text safely, never as raw HTML, and keep it separate from owner-authored discussion. Text containing `@agent` remains untrusted provider text. No data is posted into Hub discussion messages, owner intake or task creation. A later authorized task feature must preserve that provenance through a Hub-side checked transaction; this facade does not implement it.

## Cache and lifecycle boundaries

The Host creates a dedicated 0700 directory below the existing state-file parent, partitioned by a hash of exact Hub node identity and backend URL. SQLite files are 0600. Symlink/hardlink files, exposed files/directories and foreign ownership are rejected. Browser input never controls the storage path.

SQLite `application_id`, schema version 2 and an identity marker are checked before use. Unknown/unversioned populated databases, future versions and another Host's cache are rejected, not migrated, overwritten or silently rebound. The original standalone slice's unversioned cache and version 1 caches (which used inconsistent GitHub issue/PR IDs) are intentionally not adopted. All data here is a derived external snapshot cache, not the Hub ledger.

The authenticated web lifecycle owns both route and cache. Disposal removes the route, aborts provider/Hub reads, releases only this cache handle's owned leases and closes SQLite idempotently. Late I/O completion cannot commit. A single transport deadline covers header lookup, fetch and body reads; rejected or abandoned response bodies are cancelled without waiting on an uncooperative cancellation callback. Each read rechecks current Hub channel scope/audience and binding revision; an authorization revision mismatch prevents old cards or receipts from being reused. Explicit rebind establishes a clean generation. Removed capabilities block cached cards and receipt replay.

A cross-process SQLite lease prevents overlapping reads per binding. Commit checks the current binding revision and unexpired token; stale/crashed requests cannot overwrite a newer read. Channel access is checked before and after I/O, but this is not an atomic cross-service authorization transaction. A future publication path must enforce authority at the Hub transaction boundary.

## Single-page coverage and read time

The provider reports `coverage: {mode: "single_page_snapshot", observed_page, requested_limit: 100, observed_count, has_more: "unknown", reconciliation: "not_performed"}`. `observed_count` counts normalized source rows before capability filtering; receipt `observed` counts the permitted rows retained by the adapter. These values can differ, for example when an issue list contains an ungranted PR type. No response-header pagination evidence is available through the current JSON-only transport, so full, short and empty pages all keep `has_more: "unknown"`.

The Host stamps `read_at` (ISO UTC) only after the provider read succeeds, and adds the requested `kind`, explicit `parent` or `null`, and `request_id`. The resulting `last_sync` is committed with cards and the receipt in the existing SQLite transaction and stored as optional JSON in `external_bindings.body`. No schema migration or new cache version is required: existing version 2 bindings without this field are explicitly unknown. Empty and unchanged successful reads update this evidence; failures, expired leases and old exact-request replay do not. Rebinding clears it with the old authorization generation. Binding lists omit the metadata; the capability-checked cards response exposes it, including a capability check when the source returned no cards.

`last_sync` describes only the most recently committed page read, not the time or coverage of every cached card. Requests for pages in any order do not establish an ordered feed or a consistent snapshot. Old cards missing from a later page are retained, not treated as deleted. The UI displays these limits and marks cache pagination completion only as “本地快照已显示”, never as external-source completeness. Refreshing this panel reads local cached data and current authority; it does not perform a provider sync or advance `read_at`.

## Capacity guard (no eviction)

Distinct cards accumulate per binding, changed card bodies append event observations, and every new successful request ID retains an idempotent receipt even for an empty or unchanged page. Each Host cache partition now enforces fixed defaults: 128 bindings, 10,000 cards, 50,000 event observations, 20,000 receipts, and 64 MiB of logical snapshot text. These are conservative local-cache safety limits, not provider limits or an expected retention duration. The count limits bound overhead from small/empty records; the byte limit bounds large text. The larger event/receipt allowances leave room for repeated reads without assuming those reads represent an ordered provider feed.

`snapshot_bytes` counts UTF-8 bytes in every TEXT column of `external_cards`, `external_events` and `external_receipts`, including duplicated source bodies, object keys, request IDs and fingerprints. Bounded binding metadata and the at-most-one poll row per binding are limited by the binding count and existing input length checks. This is **not a physical disk quota**: SQLite pages, indexes, free pages, journals and WAL may exceed the logical total, and a long-lived external reader can delay WAL reclamation. There is no automatic eviction, receipt expiration, deletion, VACUUM or forced checkpoint. Existing explicit rebind semantics remain the only generation-clearing path; rebinding does not remove the binding itself or free a binding slot.

New bindings and new sync admissions check capacity under `BEGIN IMMEDIATE`. Receipt exhaustion rejects a fresh request before source I/O and creates no error receipt or event. Exact replay is looked up under the same lock before quota or lease admission, after the original channel, capability and authorization-revision checks. A full card/event budget can still accept an unchanged or empty successful read if its new receipt fits. A changed page is planned completely, including repeated changes to the same card within that page, then checked before snapshot writes. Commit rechecks capacity under the lock so reads on different bindings/handles cannot consume the same final slot. Rejection leaves cards, events, receipts and `last_sync` unchanged and releases only the caller's lease. Missing rows never mean deletion.

Usage is derived from existing version 2 tables; no schema migration, durable counters or browser-configurable policy is added. Normal writes update exact in-memory counts after their locked transaction. `PRAGMA data_version` detects another handle's commits; `total_changes()` detects untracked local SQL. Either invalidates the cached aggregate before the next write. Rollbacks invalidate any provisional statistics, but a read-only quota rejection does not force a new full scan on every retry. Unexpected row changes fail closed. This Host-owned schema does not support triggers: mutation of a table with a main/temp trigger is rejected inside the transaction before commit, even if its row counts appear unchanged. Triggers are never removed or repaired. Disposal also checks its lease-release writes. If an abnormal poll trigger prevents safe release, disposal closes the handle without committing that trigger's changes and the existing lease expires normally.

The first measurement or an external-writer change requires a SQL aggregate scan of current rows/text, without materializing or parsing all stored JSON in JavaScript. Existing oversized caches are not destroyed or migrated: cards and authorized exact receipts remain readable, while new snapshot writes are refused. Explicit disable/rebind and lease release remain available for ordinary caches even over the limits. A trusted constructor may lower limits for isolated tests, never widen them or enable a connection. No production settings route exists.

Local synthetic Node 24 benchmark (2026-11-10, not a performance guarantee): a 60.35 MiB logical cache with 10,000 cards, 50,000 events and 19,000 receipts took 14.9 ms for an uncached aggregate. Fifty unchanged one-card reads took 0.15 ms median / 0.24 ms p95 for lease + commit + release; cached status averaged 0.002 ms. That fixture's database was 73.2 MB and its WAL 73.7 MB, illustrating why logical bytes must not be described as a filesystem quota. Legacy caches can already exceed these sizes, so their first aggregate may take longer.

## Provider scope and remaining work

TAPD uses documented status/data/Story|Bug|Task|Comment envelopes. Gongfeng v3 paths are separate from GitLab v4, with notes explicitly opt-in. GitHub/Gitea basic adapters check the common model, not instance certification. GitHub issue/PR identities use the positive repository-local `number`, shared across `/issues` and `/pulls`; missing numbers are rejected. Other providers retain their own ID mapping. Display links are restricted to the source origin or additional trusted Host-approved origins; links in provider bodies are never fetched.

### Public API contract baseline (reviewed 2026-11-10)

TAPD's referenced public REST endpoints have no version component in their URL. This dated documentation baseline is not an instance certification or a guessed server version:

- [Comments](https://open.tapd.cn/document/api-doc/API%E6%96%87%E6%A1%A3/api_reference/comment/get_comments.html): internal parent kinds `story`, `task`, `bug` map to exact wire `entry_type` values `stories`, `tasks`, `bug`, respectively, on both requests and response checks. `entry_id` and `workspace_id` must also match. Undocumented singular aliases, case folding, `bug_remark`, and other parent types are not accepted or requested. Comment authors come from `author`.
- [Stories](https://open.tapd.cn/document/api-doc/API%E6%96%87%E6%A1%A3/api_reference/story/get_stories.html) and [Tasks](https://open.tapd.cn/document/api-doc/API%E6%96%87%E6%A1%A3/api_reference/task/get_tasks.html): normalize the documented `creator` string to the card author. Do not fall back to assignee `owner` or a guessed `author` alias. Missing creators remain unknown. Bug author aliases have not been verified and are not added by this change.
- [Gongfeng issues](https://git.tencent.com/help/menu/api/issues.html) and [merge requests](https://git.tencent.com/help/menu/api/merge_requests.html): the v3 API accepts project IDs or encoded full paths, but this adapter only supports canonical positive decimal project IDs. A path is rejected before transport because no approved path-to-ID resolution is implemented; numeric response `project_id` checks remain in place. Object identity remains the v3 global `id`, not repository-local `iid`. GitLab resource handling is unchanged.

`test/support/tapd-contract-fixture.js` contains synthetic values with documented field shapes, not account captures or complete copies of documentation examples. The Task page's sample omits an object brace, so the fixture uses valid JSON with the documented Task list wrapper. Request assertions are independent of the adapter's mapping table. Offline and isolated Hub/renderer tests cover creator display, exact comment parent/project rejection, untrusted text, owner/scope access and no task/message intake. They do not establish real-account or production connectivity acceptance. Compatibility remains `unverified-instance` by default, and the production registry remains absent/disabled.

Only explicit, bounded one-page snapshot reads exist. Missing rows never mean deletion. Full pagination/reconciliation, long-term retention management, authoritative provider revision order, webhook verification, production registry adaptation, account management and UI card insertion are not implemented. Owner-triggered reads grow cached history only within the capacity guard; this is not a certified production connector.


The Hub test creates and cleans its own temporary configuration, tokens, database and loopback process. It checks real channel authorization, durable cache/Hub restart and empty Hub message/task intake, while every provider response remains synthetic. It never connects to the daily Hub, external API or model.

## Retained compatibility

Trusted providers may restrict `allowedScopes`; immutable scope descriptors are checked for every authorization. The owner-only `connections` catalog retains channel/scope checks and exposes no transport or credential. Identical committed binds replay only when the current authorization revision also matches. These internal compatibility APIs do not enable connections or add UI actions.
